# Автоматизация поиска вакансий

## Назначение

Эта папка содержит MVP-систему для поиска и оценки вакансий, подготовки сопроводительных писем и отправки результатов в Telegram.

Система не отправляет отклики автоматически. Пользователь самостоятельно открывает вакансию, проверяет данные и отправляет отклик на hh.ru.

## Принятые решения

- Среда выполнения: существующий self-hosted n8n на VPS.
- Основной workflow: один управляемый конвейер без отдельного Python-сервиса.
- Основная программная логика: Code node с JavaScript.
- Нативные ноды используются там, где они безопаснее или удобнее для интеграции.
- Хранилище состояния MVP: n8n Data Table, создаваемая пользователем вручную.
- Источник вакансий MVP: анонимные HTML-страницы поиска и вакансий hh.ru.
- Анализ вакансий и составление писем: модели через OpenRouter.
- Выходной канал: Telegram.
- Отправка отклика: только вручную.
- Genspark Claw и Genspark Cloud Computer не используются.
- MCP-сервер для MVP не используется.
- Официальный API hh.ru остается резервным источником, если заявка будет одобрена.

## Ограничения и принятый риск

По состоянию на 13.09.2026 обычные поисковые страницы и страницы вакансий hh.ru доступны без авторизации и возвращают серверный HTML.

При этом условия hh.ru запрещают программные средства, имитирующие работу пользователя, а также автоматизированный сбор и структурирование информации. Ограничение сформулировано независимо от частоты запросов и наличия авторизации.

Пользователь принимает этот риск. Реализация должна оставаться технически щадящей и не должна включать обход защитных механизмов.

Запрещенные для проекта способы:

- обход CAPTCHA;
- ротация прокси для обхода ограничений;
- подмена browser fingerprint;
- использование cookies или сессии аккаунта hh.ru;
- автоматическая авторизация;
- автоматическое нажатие кнопки отклика;
- повторные запросы после явного запрета со стороны сайта.

Если hh.ru возвращает 403, 429 или CAPTCHA, workflow прекращает текущий сбор и отправляет диагностическое уведомление.

Источники:

- https://hh.ru/terms
- https://hh.ru/robots.txt
- https://api.hh.ru/openapi/redoc

## Фактическая архитектура

В репозитории зафиксированы три workflow.

### 01. Сбор и первичная фильтрация

Файл:

```text
workflows/01-html-source-smoke-test.json
```

Фактический конвейер:

```text
Manual Trigger
-> Generate Search URLs
-> Fetch Search Page
-> Extract Vacancy Links
-> Only New Vacancies
-> Limit New Vacancies
-> Wait Before Detail Request
-> Fetch Vacancy Page
-> Parse Vacancy Page
-> Prepare Data Table Row
-> Apply Hard Filters
-> Save Vacancy
```

Workflow:

- формирует восемь поисковых URL;
- последовательно получает поисковые страницы hh.ru;
- объединяет дубли между поисковыми запросами;
- проверяет vacancy ID в Data Table;
- ограничивает один запуск сорока новыми вакансиями;
- получает страницы новых вакансий;
- извлекает основные поля и очищенное описание;
- нормализует формат работы;
- применяет жесткие фильтры;
- сохраняет результат в `job_vacancies`.

### 03. Калибровка оценки

Файл:

```text
workflows/03-score-calibration.json
```

Фактический конвейер:

```text
Manual Trigger
-> Get Found Vacancies
-> Select Calibration Sample
-> Build Scoring Request
-> OpenRouter Score
-> Parse Scoring Response
-> Save Scoring Result
```

Workflow выбирает десять заранее заданных вакансий и выполняет тестовую оценку через OpenRouter.

Это калибровочная реализация scoring v1. Она не предназначена для массового регулярного запуска без доработки.

### 99. Повторная обработка существующих записей

Файл:

```text
workflows/99-reprocess-existing-vacancies.json
```

Фактический конвейер:

```text
Manual Trigger
-> Get Existing Vacancies
-> Normalize Existing Work Format
-> Apply Hard Filters Reprocess
-> Update Existing Vacancy
-> Reprocess Summary
```

Workflow предназначен для одноразового повторного применения нормализации и жестких фильтров к ранее сохраненным строкам без повторной загрузки страниц hh.ru.

### Целевая архитектура

После завершения scoring v2 рабочий конвейер должен дополнительно включать:

```text
Новые вакансии со status=found
-> OpenRouter scoring v2
-> детерминированная проверка score и critical gaps
-> выбор варианта резюме
-> генерация сопроводительного письма для прошедших вакансий
-> Telegram
-> обновление Data Table
```

Автоматическая отправка откликов не входит в архитектуру.

## Предпочтения по нодам n8n

Code JS используется для:

- генерации поисковых URL;
- нормализации URL;
- извлечения vacancy ID;
- очистки и парсинга HTML;
- удаления дублей внутри одного запуска;
- подготовки данных для Data Table;
- жестких фильтров;
- валидации JSON от модели;
- форматирования Telegram-сообщений;
- расчета служебных полей и статусов.

Нативные ноды предпочтительны для:

- Manual Trigger и Schedule Trigger;
- HTTP Request;
- Wait;
- Loop Over Items;
- Data Table;
- OpenRouter или HTTP Request с credentials;
- Telegram;
- IF и Switch, если условие остается простым и наглядным.

Секреты должны храниться в n8n Credentials или переменных окружения. Code JS не должен содержать API-ключи и токены.

## Получение вакансий

Поисковые запросы хранятся как конфигурация. LLM может помочь подготовить их первоначальный список, но при регулярном запуске URL создаются детерминированно кодом.

Предпочтительный порядок:

1. Получить одну страницу каждого узкого поискового запроса.
2. Извлечь ссылки вида /vacancy/{id}.
3. Привести ссылки к каноническому виду https://hh.ru/vacancy/{id}.
4. Удалить параметры аналитики и дубли.
5. Проверить vacancy ID в Data Table.
6. Загружать полную страницу только для нового vacancy ID.

Пагинация включается только после проверки качества первой страницы. Максимальное число страниц задается отдельно для каждого поискового запроса.

## Политика HTTP-запросов

- Запросы выполняются последовательно.
- Рекомендуемая начальная пауза между страницами вакансий: 3-5 секунд.
- Рекомендуемая частота полного поиска: один или два раза в сутки.
- Повторно найденная вакансия не загружается, если ее данные не требуют обновления.
- На 403 workflow останавливает текущий источник.
- На 429 workflow останавливает текущий источник и не выполняет агрессивные повторы.
- На сетевые ошибки и 5xx допускается ограниченное число повторов с увеличением задержки.
- HTML и ответы с CAPTCHA не передаются модели как вакансии.
- Cookies и данные авторизованной сессии не используются.

## Парсинг HTML

Из поисковой страницы первоначально извлекаются только:

- vacancy ID;
- канонический URL;
- поисковая конфигурация, в которой найдена вакансия.

Из отдельной страницы вакансии извлекаются:

- название;
- компания;
- зарплата;
- регион;
- формат и график работы;
- требуемый опыт;
- дата публикации;
- описание вакансии;
- признак архивной или недоступной вакансии.

Перед отправкой в OpenRouter HTML очищается от скриптов, стилей, навигации, рекламы и служебных данных.

Парсер должен иметь контролируемый fallback. Если описание не найдено, вакансии назначается статус parse_failed. В модель неполная страница автоматически не отправляется.

## Жесткие фильтры

Жесткие фильтры применяются до вызова модели и используют преимущественно название вакансии.

Текущие группы блокировки:

- продажи и развитие бизнеса;
- маркетинг, SEO и закупка трафика;
- ассистенты;
- project и product management;
- рекрутинг и HR;
- QA и автоматизация тестирования;
- ML и Data Science как основная специализация;
- чистая программная разработка;
- промышленная автоматизация;
- промышленное проектирование и инженерные специальности;
- разработка на 1С;
- заведомо не-IT роли;
- компьютерные клубы;
- арбитраж трафика.

Дополнительно проверяются:

- наличие `vacancy_id`;
- наличие URL;
- наличие названия;
- длина описания не менее 200 символов;
- соответствие географии формату работы.

Географическое правило основного workflow:

- для `remote` регион работодателя не ограничивается;
- `office`, `hybrid` и `field` допустимы только для Санкт-Петербурга и Мурино;
- `unspecified` не отклоняется жестким фильтром и передается на дальнейшую оценку.

Жесткий фильтр намеренно не отклоняет автоматически:

- DevOps и SRE;
- сетевых инженеров;
- инженеров внедрения;
- техническую поддержку;
- системных аналитиков;
- прикладных AI-инженеров;
- интеграторов API и CRM;
- вакансии без указанной зарплаты;
- вакансии с частичным совпадением технологий.

Известное расхождение: workflow 99 пока не содержит географический фильтр `location_format_mismatch`. Перед следующим массовым reprocess его код нужно синхронизировать с workflow 01.

## Работа с OpenRouter

OpenRouter не используется для поиска вакансий. Он получает очищенные и структурированные данные вакансии.

В workflow 03 реализована калибровка scoring v1:

- модель `deepseek/deepseek-v4-flash`;
- температура `0.1`;
- reasoning отключен;
- ответ ограничен строгой JSON Schema;
- score рассчитывается как сумма четырех компонентов;
- decision пересчитывается кодом;
- результат сохраняется в `analysis_json`.

Пороги scoring v1:

- 0-59: `reject`;
- 60-74: `review`;
- 75-100: `recommend`.

Калибровка подтвердила техническую работоспособность интеграции, но выявила логические проблемы:

- завышение оценки при отсутствии критической специализации;
- отдельные неподтвержденные утверждения;
- штрафы за образование, английский и технологии, которые вакансия не требует;
- противоречия между decision и `cover_letter_recommended`.

Перед массовым запуском требуется scoring v2. Его контракт описан в `PROMPTS.md`, а результаты калибровки - в `CALIBRATION.md`.

В scoring v2 значения `score`, `decision` и `cover_letter_recommended` должны окончательно определяться Code JS, а не приниматься от модели без проверки.

Следующая техническая версия должна заменить отдельную тестовую HTTP Request ноду прямым вызовом OpenRouter из Code JS через переменную окружения `OPENROUTER_API_KEY`.

## Telegram

Для каждой рекомендованной вакансии отправляются:

- score;
- название и компания;
- зарплата и формат работы;
- ссылка;
- основные совпадения;
- пробелы и риски;
- рекомендованный вариант резюме;
- сопроводительное письмо.

В будущей версии допускаются кнопки:

- Откликнулся;
- Пропустить;
- Приоритет;
- Переписать письмо.

Кнопки изменяют только статус в Data Table. Они не отправляют отклик на hh.ru.

## Data Table

Таблица создается пользователем вручную. Рекомендуемые поля описаны в DATATABLE.md.

Перед первым импортом workflow нужно проверить, что имя таблицы и названия колонок совпадают с настройками нод.

## Данные кандидата

Существующие подтвержденные данные резюме и проекта не дублируются в этой папке автоматически.

Перед реализацией LLM-части нужно определить компактные источники:

- подтвержденный профиль кандидата;
- варианты резюме;
- проекты и кейсы;
- ограничения и стоп-факторы;
- правила выбора варианта резюме.

Эти данные должны использовать доказательную модель проекта и не должны превращать гипотезы в факты.

## Резервный официальный источник

Если hh.ru одобрит заявку на приложение, API можно добавить как отдельный источник поиска. Соискательские операции и автоматические отклики в архитектуру не добавляются без отдельной проверки доступности и правил.

## Критерии готовности MVP

MVP считается готовым, если:

- workflow получает поисковую страницу;
- корректно выделяет уникальные vacancy ID;
- не загружает уже обработанные вакансии;
- извлекает читаемое описание новой вакансии;
- применяет жесткие фильтры до вызова модели;
- получает валидный structured score;
- составляет письмо без выдуманных фактов;
- отправляет результат в Telegram;
- сохраняет статус в Data Table;
- безопасно останавливается при 403, 429 и изменении HTML.
