# Автоматизация поиска вакансий

## Назначение

Эта папка содержит MVP-систему для поиска и оценки вакансий, подготовки сопроводительных писем и отправки результатов в Telegram.

Система не отправляет отклики автоматически. Пользователь самостоятельно открывает вакансию, проверяет данные и отправляет отклик на hh.ru.

## Принятые решения

- Среда выполнения: существующий self-hosted n8n на VPS.
- Основной workflow: один управляемый конвейер без отдельного Python-сервиса.
- Основная программная логика: Code node с JavaScript.
- Нативные ноды используются там, где они безопаснее или удобнее для интеграции.
- Хранилище состояния MVP: n8n Data Table, создаваемая пользователем вручную.
- Источник вакансий MVP: анонимные HTML-страницы поиска и вакансий hh.ru.
- Анализ вакансий и составление писем: модели через OpenRouter.
- Выходной канал: Telegram.
- Отправка отклика: только вручную.
- Genspark Claw и Genspark Cloud Computer не используются.
- MCP-сервер для MVP не используется.
- Официальный API hh.ru остается резервным источником, если заявка будет одобрена.

## Ограничения и принятый риск

По состоянию на 13.09.2026 обычные поисковые страницы и страницы вакансий hh.ru доступны без авторизации и возвращают серверный HTML.

При этом условия hh.ru запрещают программные средства, имитирующие работу пользователя, а также автоматизированный сбор и структурирование информации. Ограничение сформулировано независимо от частоты запросов и наличия авторизации.

Пользователь принимает этот риск. Реализация должна оставаться технически щадящей и не должна включать обход защитных механизмов.

Запрещенные для проекта способы:

- обход CAPTCHA;
- ротация прокси для обхода ограничений;
- подмена browser fingerprint;
- использование cookies или сессии аккаунта hh.ru;
- автоматическая авторизация;
- автоматическое нажатие кнопки отклика;
- повторные запросы после явного запрета со стороны сайта.

Если hh.ru возвращает 403, 429 или CAPTCHA, workflow прекращает текущий сбор и отправляет диагностическое уведомление.

Источники:

- https://hh.ru/terms
- https://hh.ru/robots.txt
- https://api.hh.ru/openapi/redoc

## Фактическая архитектура

В репозитории зафиксированы три workflow.

### 01. Сбор и первичная фильтрация

Файл:

```text
workflows/01-html-source-smoke-test.json
```

Фактический конвейер:

```text
Manual Trigger
-> Generate Search URLs
-> Fetch Search Page
-> Extract Vacancy Links
-> Only New Vacancies
-> Limit New Vacancies
-> Wait Before Detail Request
-> Fetch Vacancy Page
-> Parse Vacancy Page
-> Prepare Data Table Row
-> Apply Hard Filters
-> Save Vacancy
```

Workflow:

- формирует восемь поисковых URL;
- последовательно получает поисковые страницы hh.ru;
- объединяет дубли между поисковыми запросами;
- проверяет vacancy ID в Data Table;
- ограничивает один запуск шестьюдесятью новыми вакансиями;
- получает страницы новых вакансий;
- извлекает основные поля и очищенное описание;
- нормализует формат работы;
- применяет жесткие фильтры;
- сохраняет результат в `job_vacancies`.

### 03. Production-оценка вакансий

Файл:

```text
workflows/03-score-found-vacancies.json
```

Фактический основной конвейер:

```text
Manual Trigger
-> Get Found Vacancies
-> Limit Scoring Batch
-> Build Scoring Request
-> OpenRouter Score
-> Parse Scoring Response
-> Save Scoring Result
```

Параллельно после `Parse Scoring Response` работает `Scoring Export`, который формирует компактную выгрузку без `description_text` и полного `analysis_json`.

Workflow:

- выбирает строки со status `found`;
- ограничивает один запуск управляемым пакетом;
- строит scoring v2 request;
- вызывает OpenRouter непосредственно из Code JS;
- получает API-ключ через `$env.OPENROUTER_API_KEY`;
- использует `await this.helpers.httpRequest()`;
- проверяет и нормализует structured JSON;
- детерминированно вычисляет score и decision;
- применяет critical gap и salary blockers;
- обновляет строку Data Table со status `scored`.

Дата оценки передается через `$now`, а не фиксируется в prompt.

### 99. Служебная повторная обработка

Файл:

```text
workflows/99-reprocess-vacancies.json
```

Workflow содержит ручные служебные ветки для повторной обработки уже сохраненных строк без повторной загрузки вакансий с hh.ru.

В нем сохранены:

- нормализация существующего `work_format`;
- повторное применение hard filters;
- обновление существующих строк;
- сводка результатов;
- повторный расчет salary blockers для строк со status `scored`;
- компактный экспорт измененных зарплатных решений.

Manual Trigger при необходимости перецепляется к требуемой служебной ветке.

Salary reprocess использует сохраненные `description_text`, `score_breakdown` и `analysis_json`. Повторный вызов OpenRouter для этого не требуется.

### Целевая архитектура

После завершения scoring v2 рабочий конвейер должен дополнительно включать:

```text
Новые вакансии со status=found
-> OpenRouter scoring v2
-> детерминированная проверка score и critical gaps
-> выбор варианта резюме
-> генерация сопроводительного письма для прошедших вакансий
-> Telegram
-> обновление Data Table
```

Автоматическая отправка откликов не входит в архитектуру.

## Предпочтения по нодам n8n

Code JS используется для:

- генерации поисковых URL;
- нормализации URL;
- извлечения vacancy ID;
- очистки и парсинга HTML;
- удаления дублей внутри одного запуска;
- подготовки данных для Data Table;
- жестких фильтров;
- валидации JSON от модели;
- форматирования Telegram-сообщений;
- расчета служебных полей и статусов.

Нативные ноды предпочтительны для:

- Manual Trigger и Schedule Trigger;
- HTTP Request;
- Wait;
- Loop Over Items;
- Data Table;
- OpenRouter или HTTP Request с credentials;
- Telegram;
- IF и Switch, если условие остается простым и наглядным.

Секреты должны храниться в n8n Credentials или переменных окружения. Code JS не должен содержать API-ключи и токены.

## Получение вакансий

Поисковые запросы хранятся как конфигурация. LLM может помочь подготовить их первоначальный список, но при регулярном запуске URL создаются детерминированно кодом.

Предпочтительный порядок:

1. Получить одну страницу каждого узкого поискового запроса.
2. Извлечь ссылки вида /vacancy/{id}.
3. Привести ссылки к каноническому виду https://hh.ru/vacancy/{id}.
4. Удалить параметры аналитики и дубли.
5. Проверить vacancy ID в Data Table.
6. Загружать полную страницу только для нового vacancy ID.

Пагинация включается только после проверки качества первой страницы. Максимальное число страниц задается отдельно для каждого поискового запроса.

## Политика HTTP-запросов

- Запросы выполняются последовательно.
- Рекомендуемая начальная пауза между страницами вакансий: 3-5 секунд.
- Рекомендуемая частота полного поиска: один или два раза в сутки.
- Повторно найденная вакансия не загружается, если ее данные не требуют обновления.
- На 403 workflow останавливает текущий источник.
- На 429 workflow останавливает текущий источник и не выполняет агрессивные повторы.
- На сетевые ошибки и 5xx допускается ограниченное число повторов с увеличением задержки.
- HTML и ответы с CAPTCHA не передаются модели как вакансии.
- Cookies и данные авторизованной сессии не используются.

## Парсинг HTML

Из поисковой страницы первоначально извлекаются только:

- vacancy ID;
- канонический URL;
- поисковая конфигурация, в которой найдена вакансия.

Из отдельной страницы вакансии извлекаются:

- название;
- компания;
- зарплата;
- регион;
- формат и график работы;
- требуемый опыт;
- дата публикации;
- описание вакансии;
- признак архивной или недоступной вакансии.

Перед отправкой в OpenRouter HTML очищается от скриптов, стилей, навигации, рекламы и служебных данных.

Парсер должен иметь контролируемый fallback. Если описание не найдено, вакансии назначается статус parse_failed. В модель неполная страница автоматически не отправляется.

## Жесткие фильтры

Жесткие фильтры применяются до вызова модели и используют преимущественно название вакансии.

Текущие группы блокировки:

- продажи и развитие бизнеса;
- маркетинг, SEO и закупка трафика;
- ассистенты;
- project и product management;
- рекрутинг и HR;
- QA и автоматизация тестирования;
- ML и Data Science как основная специализация;
- чистая программная разработка;
- промышленная автоматизация;
- промышленное проектирование и инженерные специальности;
- разработка на 1С;
- заведомо не-IT роли;
- компьютерные клубы;
- арбитраж трафика.

Дополнительно проверяются:

- наличие `vacancy_id`;
- наличие URL;
- наличие названия;
- длина описания не менее 200 символов;
- соответствие географии формату работы.

Географическое правило основного workflow:

- для `remote` регион работодателя не ограничивается;
- `office`, `hybrid` и `field` допустимы только для Санкт-Петербурга и Мурино;
- `unspecified` не отклоняется жестким фильтром и передается на дальнейшую оценку.

Жесткий фильтр намеренно не отклоняет автоматически:

- DevOps и SRE;
- сетевых инженеров;
- инженеров внедрения;
- техническую поддержку;
- системных аналитиков;
- прикладных AI-инженеров;
- интеграторов API и CRM;
- вакансии без указанной зарплаты;
- вакансии с частичным совпадением технологий.

Известное расхождение: workflow 99 пока не содержит географический фильтр `location_format_mismatch`. Перед следующим массовым reprocess его код нужно синхронизировать с workflow 01.

## Работа с OpenRouter

OpenRouter не используется для поиска вакансий. Он получает очищенные структурированные данные вакансии и профиль кандидата.

Production scoring v2 реализован в:

```text
workflows/03-score-found-vacancies.json
```

Основные параметры и правила:

- модель `deepseek/deepseek-v4-flash`;
- температура `0.1`;
- reasoning отключен;
- используется строгая JSON Schema;
- текущая дата передается через `$now`;
- прямой запрос выполняется из Code JS;
- API-ключ читается из `$env.OPENROUTER_API_KEY`;
- score пересчитывается из `score_breakdown`;
- critical gap ограничивает score значением 59;
- decision вычисляется Code JS;
- `cover_letter_recommended` вычисляется Code JS;
- ключ и Authorization header не сохраняются.

Пороги:

- 0-59: `reject`;
- 60-74: `review`;
- 75-100: `recommend`.

Зарплатные минимумы на руки:

- `ai_automation`: 120000 рублей;
- `it_infrastructure`: 100000 рублей.

Если зарплата отсутствует или указана только нижняя граница, salary hard reject не применяется.

Если известная верхняя граница ниже минимального порога, Code JS добавляет:

```text
salary_below_minimum
```

и устанавливает:

```text
score <= 59
decision = reject
cover_letter_recommended = false
```

Верхняя граница извлекается из структурированного поля `salary`, а при его отсутствии - из зарплатного контекста `description_text`.

## Критерии готовности MVP

MVP считается готовым, если:

- workflow получает поисковую страницу;
- корректно выделяет уникальные vacancy ID;
- не загружает уже обработанные вакансии;
- извлекает читаемое описание новой вакансии;
- применяет жесткие фильтры до вызова модели;
- получает валидный structured score;
- составляет письмо без выдуманных фактов;
- отправляет результат в Telegram;
- сохраняет статус в Data Table;
- безопасно останавливается при 403, 429 и изменении HTML.

## Стратегия массовых откликов

Цель автоматизации - подготовить широкий поток правдивых откликов, а не заменить решение пользователя или работодателя.

- План на ближайшие две недели: до 500 ручных откликов.
- Score и decision определяют порядок обработки.
- Critical gap является предупреждением, но сам по себе не запрещает подготовку письма.
- Отсутствие отдельной технологии не является hard blocker, если направление работы соответствует одному из вариантов резюме.
- Подтвержденная способность быстро осваивать новый стек учитывается при оценке и подготовке письма.
- Система не должна заявлять опыт с технологией, если такого опыта нет в профиле.
- Письма создаются автоматически для вакансий с допустимым вариантом резюме и без объективного hard blocker.
- Окончательная проверка и отправка отклика на hh.ru выполняются пользователем.

Следующий production workflow:

```text
Job Search - 04 Generate Cover Letters
```

После него готовые вакансии и письма передаются в Telegram для быстрого ручного отклика.

## Текущая операционная политика массовых откликов

Приоритет текущего этапа - подготовка максимально широкого потока правдивых ручных откликов.

Обычное действие пользователя:

```text
открыть ссылку из Telegram
-> выбрать указанное резюме
-> скопировать сопроводительное письмо
-> отправить отклик на hh.ru
```

Отдельная регулярная ручная проверка очереди `letter_review` в рабочий процесс не закладывается. Поэтому система должна направлять туда только письма с конкретным риском ложного или существенно вводящего в заблуждение утверждения.

Несовпадения географии, формата, названия роли, отдельных технологий и других данных вакансии не требуют дальнейшего автоматического ужесточения без подтвержденной критической проблемы. Работодатель видит резюме, географию и условия кандидата и также выполняет собственный отбор.

Если необходимого инструмента нет в подтвержденном опыте, письмо может указывать готовность быстро его освоить, но не должно утверждать, что кандидат уже применял этот инструмент.

## Production-оркестратор

Production-оркестратор хранится в:

```text
workflows/00-scheduled-orchestrator.json
```

Внутреннее имя:

```text
Job Search - 00 Scheduled Orchestrator
```

Цепочка:

```text
Manual Trigger / Schedule Trigger
-> Orchestrator Settings
-> Execute Workflow 01 - Collect Vacancies
-> Execute Workflow 03 - Score Vacancies
-> Execute Workflow 04 - Generate Letters
-> Execute Workflow 05 - Send To Telegram
```

Дочерние workflow не передают друг другу вакансии. Каждый этап самостоятельно читает свою очередь из Data Table:

- workflow 01 создаёт новые записи;
- workflow 03 читает все записи `found`;
- workflow 04 читает все записи `scored`;
- workflow 05 читает все записи `letter_ready` и `letter_review`.

На каждой Execute Sub-workflow ноде включены:

```text
Execute Once
Always Output Data
Wait for Sub-Workflow Completion
```

`On Error` установлен в `Stop Workflow`. Отдельный Error Handler отправляет владельцу уведомление в Telegram о настоящих ошибках выполнения.

### Расписание

Timezone workflow:

```text
Europe/Moscow
```

Cron:

```text
0 0 4,10,16 * * *
```

Запуски происходят в 04:00, 10:00 и 16:00 по Москве, что соответствует 08:00, 14:00 и 20:00 в Алтайском крае.

Workflow с Schedule Trigger должен быть опубликован и активирован после ручной проверки.

### Стратегия пропускной способности

Workflow 01 добавляет не более 60 новых вакансий за запуск. Расширенная поисковая конфигурация использует несколько формулировок для двух направлений, Санкт-Петербург и удалённую работу, а также несколько страниц выдачи.

Последующие workflow не используют искусственный batch limit:

- workflow 03 обрабатывает все `found`;
- workflow 04 обрабатывает все `scored`;
- workflow 05 отправляет все `letter_ready` и `letter_review`.

Это предотвращает накопление устаревающих вакансий между scheduled-запусками.

### Первый чистый запуск

Первый успешный полный запуск оркестратора обработал 40 новых вакансий:

```text
workflow 01: 40 items, около 553 секунд
workflow 03: 18 items, около 380 секунд
workflow 04: 13 items, около 159 секунд
workflow 05: 13 items, около 30 секунд
```

Итог:

```text
filtered: 22
application_blocked: 5
sent_to_telegram: 13
```

В Telegram успешно доставлены 13 вакансий с выбранным резюме и сопроводительным письмом.

### Исправленный инцидент с размножением items

При первом ошибочном запуске workflow 01 передал оркестратору 40 items. Нода вызова workflow 03 использовала `Run once with all items`, но не имела `Execute Once`. В результате дочерний workflow получил 40 управляющих items и многократно прочитал одну очередь Data Table.

До остановки выполнения было обработано около 720 повторяющихся items.

Причина устранена включением `Execute Once` на всех Execute Sub-workflow нодах. В дочерний workflow теперь передаётся один технический item, а рабочие данные читаются из Data Table.

## Решения после контрольного теста рефакторинга писем

Workflow 04 переведен на `deepseek/deepseek-v4-pro` и использует два раздельных runtime-профиля. В модель передается только профиль, выбранный по `recommended_resume`.

Контрольный тест на 10 вакансиях подтвердил сохранение абзацев, отсутствие плейсхолдеров и отсутствие смешивания профилей. Девять писем получили `letter_ready`, одно обоснованно получило `letter_review`.

Подтверждено знакомство с GetCourse, Bitrix24 и WhatsApp API без реального практического опыта. Упоминание таких продуктов в письме требует `letter_review`.

Также подтверждено тестирование собственных решений: повторные проверки после изменений и исправлений, unit-тесты Python-компонента, автоматизированные проверки, QA-матрица 18 из 18 позиций, проверка deploy, backup и rollback. Этот опыт не приравнивается к коммерческому стажу QA/AQA.

Следующий этап:

- убрать безусловную фильтрацию QA/AQA и full-stack вакансий по названию;
- передавать их в scoring;
- учитывать профильные пробелы через score и critical gaps;
- усилить фильтрацию АСУ ТП, КИПиА, PLC, SCADA, электрических схем, щитов управления и другой промышленной автоматизации;
- не использовать географию как автоматический application blocker;
- сохранить широкий поток правдивых откликов.

## Корректировки фильтрации и генерации писем от 18.09.2026

Статус: реализовано через UI n8n, контрольный прогон на 20 новых вакансиях выполняется.

### Актуальная политика hard filters

География и формат работы не являются hard blockers.

Для вакансий вне Санкт-Петербурга и Мурино:

- remote полностью допустим;
- office, hybrid, field и unspecified передаются в scoring;
- несовпадение географии и формата фиксируется как аналитический риск;
- риск может снижать `conditions_fit`, но не должен устанавливать `critical_gap`, `application_blocked` или запрещать генерацию письма.

QA, AQA, full-stack и другие смежные роли не исключаются только по названию. Такие вакансии передаются в scoring, если описание содержит потенциально релевантные задачи автоматизации, интеграций, инфраструктуры, тестирования или AI.

Промышленная автоматизация остаётся hard filter. Фильтр анализирует название и описание вакансии и использует прямые либо сочетанные признаки АСУ ТП, КИПиА, PLC/ПЛК, SCADA, промышленных контроллеров, электрических схем, шкафов управления, EPLAN и других производственных технологий.

Объективными blockers остаются:

- известная верхняя граница зарплаты ниже минимального порога выбранного резюме;
- архивированная или недоступная вакансия;
- невозможность выбрать допустимый вариант резюме;
- отсутствующие или повреждённые обязательные данные.

`score`, `decision`, `critical_gap`, название роли, география и отсутствие отдельной технологии сами по себе не блокируют подготовку письма.

### Актуальная постобработка сопроводительных писем

Workflow 04 выполняет детерминированную постобработку результата модели:

- преобразует буквальный символ `↵` в настоящий перевод строки;
- нормализует переводы строк и публичный текст;
- не обрезает элементы `facts_used` внутри слова или предложения;
- объединяет части одного факта, если модель ошибочно разделила незавершённую фразу;
- ограничивает результат тремя законченными фактами;
- удаляет отдельные мета-фразы, начинающиеся с «это подтверждает», «такой подход подходит» или «это даёт понимание»;
- проверяет потенциально неподтверждённые заявления о CRM, CI/CD и профессиональном QA/AQA;
- переводит письма с конкретным риском неподтверждённого утверждения в `letter_review`.

System prompt сохранён компактным. Основная нормализация и проверка выполняются JavaScript-кодом, а не дополнительными длинными инструкциями модели.

Фразы самоотказа не перегенерируются ретроспективно. Записи предыдущего теста с такими письмами удалены пользователем. Для новой генерации prompt запрещает строить письмо вокруг отсутствующего опыта и использовать формулировки «не могу подтвердить», «не буду позиционировать» и «не заменяет коммерческий опыт».

### Текущий контрольный прогон

Для контрольного прогона лимит workflow 01 временно установлен в 20 новых вакансий.

Последовательность проверки:

1. workflow 01 собирает и фильтрует новые вакансии;
2. workflow 03 выполняет scoring;
3. workflow 04 формирует и проверяет письма;
4. workflow 05 до принятия результатов не запускается.

После анализа контрольной выборки будет принято отдельное решение о возврате лимита 60 и production-запуске.

## Production-приёмка workflow 04 и переход на пакет 60

Дата: 20.09.2026.

После исправления генерации и проверки сопроводительных писем выполнены последовательные контрольные прогоны:

- первая выборка из 13 писем использовалась для проверки форматирования и шаблонных мета-выводов;
- новый пакет из 20 вакансий дал 11 писем после корректной фильтрации остальных вакансий;
- отдельный контрольный прогон после исправления маршрутизации дал 8 `letter_ready` и 3 обоснованных `letter_review`.

Подтверждено:

- абзацы и приветствие сохраняются;
- выбранные runtime-профили не смешиваются;
- модель не получает оба резюме одновременно;
- запрещенные мета-выводы обнаруживаются Unicode-aware проверкой и вызывают одну корректирующую генерацию;
- остаточные мета-выводы переводят письмо в `letter_review`;
- упоминание Bitrix24, GetCourse, WhatsApp API и отдельных неподтвержденных предметных систем контролируется детерминированно;
- SQLite не расширяется до профессионального опыта написания и оптимизации SQL-запросов;
- общие инфраструктурные операции не приписываются непосредственно 1С;
- предупреждения модели о несовпадении с вакансией сохраняются в `analysis_json.cover_letter_generation.model_warnings`, но сами по себе не блокируют правдивое письмо;
- итоговый `letter_ready` или `letter_review` определяется детерминированными проверками публичного текста.

`letter_review` остается обязательным при конкретном риске ложного или существенно вводящего в заблуждение утверждения. Низкое соответствие вакансии, отсутствие профильного образования или отдельной технологии сами по себе не переводят правдивое письмо в `letter_review`.

Контрольная выборка принята для production. Лимит новых вакансий workflow 01 увеличен с 20 до 60 за запуск. Workflow 03-05 продолжают осушать свои очереди без искусственного ограничения.

Целевая пропускная способность:

- до 60 новых вакансий за один запуск;
- три scheduled-запуска в сутки;
- фактическое количество писем зависит от дедупликации, hard filters и объективных application blockers;
- все отклики на hh.ru по-прежнему отправляются пользователем вручную.
